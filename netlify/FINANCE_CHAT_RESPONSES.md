# Gemini recommendations and response validation

## Investigation

The reported “unsupported or unverified financial answer” text was generated by
FinSight's `invalid()` helper in `developmentConversation.js`, not by a Gemini
HTTP/quota error. Its `origin: provider` caused the client to prepend “Gemini
provider.” The same helper covered several different failures:

- A planner-invented savings target that was not present in the request/scope.
- Unsupported response properties or comparison-card IDs.
- Invalid answer shape, unknown/malformed fact placeholders or excessive length.
- Any digit, currency/percentage sign **or number word** outside placeholders.

The final catch discarded the actual validation exception. In particular,
`resolveAnswer("One practical change is to review optional purchases.", {})`
failed its `numericWords.test(stripped)` condition even though it contained no
financial figure. This false rejection is reproduced in a regression test. Raw
percentage advice and numbered lists also failed that strict guard.

The historical second-turn JSON was not retained. Therefore its exact failed
subrule cannot be reconstructed from the generic displayed message. This change
does not claim that the historical model response contained a particular word,
card ID or number, or that quota caused the failure.

## Second-turn lifecycle after the correction

1. The existing client sends bounded recent user/assistant text and versioned
   financial scope to the authenticated Netlify route. Recent assistant text is
   context, never numerical evidence. The verified Firebase UID remains the only
   authority for record access.
2. Gemini interprets the complete question and inherits relevant scope. The
   backend validates dates, category/method, operation, optional target and
   optional percentage reduction before retrieving records. Forbidden tool
   fields and unrequested targets/rates fail before any retrieval.
3. Firestore retrieval remains read-only and authenticated. The existing engine
   calculates the selected amounts and category breakdown from canonical records.
4. Current facts, their kinds, allowed cards and relevant conversation go back to
   Gemini. It produces a placeholder-based answer or typed sections. Backend
   validation resolves references before returning the existing answer/cards UI
   response; no rich-response redesign or new local response templates are used.

## Response contract

`developmentResponse.js` supports `cardIds` plus exactly one of `answer` or
`sections`. The flat answer remains compatible with existing factual responses.
Advice prefers sections with `kind` and `text`:

| Kind | Validation/rendering |
| --- | --- |
| `recorded` | Requires current recorded fact references; scenario/target values cannot be presented as recorded results. |
| `hypothetical` | Requires current scenario facts; rendered with a backend-supplied estimate label, exact period and incomplete-period disclosure when applicable. |
| `recommendation` | Allows qualitative suggestions without requiring a transaction reference. Numerical financial claims still require fact placeholders. |

Ordinary counts of proposed actions, such as “one practical change” and “three
useful improvements,” are permitted. Raw amounts, percentages, dates, recorded
counts, unknown references and malformed placeholders remain rejected. Explicit
assertions of unsupported personal causes, achieved savings and classifications
such as “your shopping is unnecessary” are rejected. These checks are output
guards, not intent routing rules. They cannot prove the semantics of every
possible qualitative sentence; model judgment remains subject to these boundaries.

The schema uses Gemini's supported JSON Schema features, including `anyOf`.
[Official structured-output documentation](https://ai.google.dev/gemini-api/docs/structured-output)
describes these features; application-level financial validation remains necessary.

## Hypothetical calculations and retained context

The query contract adds optional `reductionBps` (integer basis points, from zero
through 10000). A requested 20% reduction is 2000 basis points. The rate must be
present in the current percentage request or validated previous scope; the model
cannot invent it. Existing version-two scopes without this property still work.

The backend calculates saving/remaining spending using integer arithmetic and
half-up paise rounding, with BigInt intermediates. `original = saving + remaining`
always holds. The selected category, dates, payment filter, task, savings target
and rate persist in the returned scope and are supplied on follow-ups. Scenario
facts never claim that savings have happened or establish monthly feasibility.
Explicit percentage questions require the requested rate and calculated saving
references in the final answer; generic advice or a different default cut cannot
silently replace that scenario.

## Bounded correction and accurate errors

A valid development answer still uses the normal planner and explanation calls.
An invalid JSON/schema/reference/financial response can receive **one extra model
call for the entire turn**, shared between planning and explanation. Feedback
contains only a fixed stage, rule and correction instruction. It reuses the same
authorized context; rejected text is not copied into feedback, and correction
does not re-fetch records. The existing request deadline, cancellation, privacy,
rate/concurrency limits and bounded HTTP-503 retry remain active.

API errors, tool errors, conversation errors, blocked/incomplete responses,
forbidden tool requests and unrequested scenario parameters do not trigger an
output-correction attempt. Failed corrections remain retryable errors, with no
local substitution or false Gemini success label.

| Origin | Examples |
| --- | --- |
| `provider` | Actual Gemini HTTP/transport/auth/quota/deadline errors, including provider status when available |
| `model_output` | Invalid JSON/schema, unknown facts, unverified figures, unsupported claims or tool requests |
| `tool` | Authenticated record retrieval or backend financial calculation failure |
| `conversation` | Invalid retained scope or message history |
| `configuration` / `privacy` | Existing configuration, consent and data-handling restrictions |

Model validation failures return safe `validation.stage`, `validation.rule` and
`validation.correctionAttempted` fields. The client uses “Response validation,”
“Financial tools” or “Conversation” prefixes instead of mislabelling them as
provider failures. No prompts, invalid responses, records, keys or tokens are
logged or included in validation diagnostics.

No model/configuration change or additional environment variable is required.
The integration tests select `gemini-3.1-flash-lite` through `GEMINI_MODEL` and use
the official SDK with fully mocked transport. The configured model is not replaced.

All 187 automated tests, ESLint and the production/PWA build passed. Existing
bundle-size and outdated Browserslist warnings remain. These tests establish routing, contracts, context,
privacy and deterministic numerical behavior; they do not establish live-model
response quality or live connectivity. No application, browser preview or Netlify
Dev was started, and nothing was deployed.
